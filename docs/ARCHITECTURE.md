# lolssd: архитектура

Внешний SSD с урезанной Windows и League of Legends. Подключаешь к любому компьютеру с Linux,
загружаешься с него и играешь. По желанию твой Linux продолжает работать внутри этой Windows:
та же установка с внутреннего диска, а не копия.

**Ничего не устанавливается в Linux заранее.** Всё, что нужно от системы, делает утилита,
лежащая на самом SSD: подключил, запустил с диска, готово. Утилита по возможности ничего не
меняет на хосте, а каждое изменение явно оговорено (§5).

> Проверено только на конкретном железе автора. На другом может не заработать, ничего не обещаю.

Пометка **[проверить]** означает предположение, которое ещё не проверено на железе.

---

## 1. Как этим пользоваться

**Только игра:**
1. Подключить SSD. Раздел `LOLSSD` монтируется автоматически, как обычная флешка.
2. `LOLSSD/host/lolssd check`: подходит ли машина (§3).
3. `LOLSSD/host/lolssd boot`: перезагрузиться в Windows на SSD. Без утилиты можно через
   меню загрузки прошивки (F12 / F8 / Esc).
4. Играть. Выключить, вытащить SSD, и следующая загрузка, как обычно, идёт в Linux.

**С Linux внутри Windows (по желанию):**
1. Один раз на этой машине: `lolssd profile` описывает твою систему и сохраняет описание на SSD (§6).
2. `lolssd boot`, в Windows — ярлык «Linux desktop (host)»: твой Linux в ВМ на весь экран
   каждого монитора.

## 2. Обязательства перед хостом

Суть проекта: SSD можно подключить к чужой машине, и он ей ничего не сломает.

| Риск | Как SSD его закрывает |
|---|---|
| Windows монтирует внутренние диски хоста и пишет на них (включая ESP хоста) | Портативный режим Windows (`PortableOperatingSystem`) плюс SAN policy «Offline Internal»: внутренние диски остаются Offline. Исключение — режим «Linux внутри Windows»: диски хоста из профиля целиком получает ВМ, а не Windows (§6). |
| Windows добавляет себя в NVRAM хоста и встаёт первой в `BootOrder` | Загрузчик лежит по запасному пути `\EFI\BOOT\BOOTX64.EFI` на ESP самого SSD, запись в NVRAM не нужна. При каждом старте Windows `lolssd-win nvram-guard` убирает из `BootOrder` все записи, ведущие на ESP SSD (по GUID раздела), а созданные Windows удаляет. Запись `lolssd` от утилиты хоста только убирается из порядка. [проверить] Создаёт ли Windows такую запись при загрузке с USB. |
| Часы хоста уезжают на смещение часового пояса | `RealTimeIsUniversal=1`: Windows считает RTC временем UTC, как Linux. |
| После Windows NTFS «грязный», висит гибернация | Fast Startup и гибернация выключены. Портативный режим делает это и сам. |
| BitLocker / шифрование устройства привязывается к TPM хоста | Шифрование выключено и заблокировано политикой. |
| Windows внезапно обновляется и перезагружается | Обновления выключены полностью. Windows заморожена. |
| Режим «Linux внутри Windows» ломает систему хоста | Система хоста грузится в ВМ своим ядром со своих дисков, как на железе. Всё, что ей нужно только в ВМ, передаётся при загрузке в память (учётные данные systemd через SMBIOS, §6); на диск хоста проект ничего не пишет. |
| Linux хоста был в гибернации, и ВМ открывает его диск | Портит файловую систему. [сделать] Проверять перед запуском ВМ, что хост выключен чисто. |

## 3. Требования к компьютеру

Это требования к прошивке, не к Linux. `lolssd check` проверяет всё, что видно из Linux.

| Что | Почему | Как проверяет `check` |
|---|---|---|
| UEFI (не Legacy/CSM) | Vanguard требует UEFI (VAN 9005) | `/sys/firmware/efi` |
| TPM 2.0 (AMD fTPM / Intel PTT) | Vanguard (VAN 9001) | `/sys/class/tpm/tpm0/tpm_version_major` |
| Виртуализация (SVM / VT-x) | VBS / HVCI (VAN 9005), ВМ с Linux хоста | флаги `svm`/`vmx` в `/proc/cpuinfo` плюс `dmesg` на «disabled by BIOS» |
| **Secure Boot** [проверить] | возможно, требуется Vanguard'у | переменная `SecureBoot` в efivarfs. Если нужен, а Linux хоста не подписан, Secure Boot придётся включать перед игрой и выключать после. Это ручное действие в BIOS. |
| Порт USB 10 Гбит/с | скорость | скорость SSD в `/sys/bus/usb/devices/*/speed` |
| Память | для режима Linux внутри Windows | `/proc/meminfo` |

[проверить] Требования различаются для Windows 10 и 11. В справке Riot про TPM (VAN 9001)
стоит «Win 11 Only», то есть на Windows 10 требований может быть меньше, и это расширит
круг подходящих машин. Нужно проверить, обязателен ли на Windows 10 Secure Boot.

## 4. Содержимое SSD

### Разметка

| Раздел | Размер | Назначение |
|---|---|---|
| ESP, FAT32 | 260–512 МБ | `\EFI\BOOT\BOOTX64.EFI` + `\EFI\Microsoft\Boot` |
| `LOLSSD`, FAT32 | 256 МБ | утилита для Linux, профили хостов, документация. FAT32 читается везде: и в Linux, и в Windows. |
| MSR | 16 МБ | служебный раздел Windows |
| Windows, NTFS | остальное | система, игра, QEMU для ВМ с Linux хоста |

Диск: NVMe в USB-корпусе (UASP + TRIM) или SATA в корпусе. Минимум ~64 ГБ без Linux
внутри Windows, нормально 128 ГБ.

### Windows

- **Версия:** 11 Home (проверено у автора). В Home нет управления ВМ Hyper-V, поэтому ВМ —
  QEMU на платформе гипервизора Windows (WHPX), она есть и в Home.
- **Сборка:** урезается самостоятельно из официального ISO (по образцу tiny11builder). Убрать:
  приложения из магазина, рекламу, телеметрию, OneDrive. **Оставить:** VBS / HVCI, поддержку
  TPM, Windows Hypervisor Platform (ВМ), Defender (если его отсутствие мешает HVCI [проверить]).
- **Обновления:** выключены службы `wuauserv`, `UsoSvc`, `WaaSMedicSvc` и политиками.
- **Без учётной записи Microsoft:** локальный пользователь, автоматический вход.
- **Активация:** если в прошивке хоста зашит ключ OEM (таблица ACPI MSDM) и редакция совпадает,
  Windows активируется сама. Иначе работает без активации, с водяным знаком.
  Лицензирование — ответственность пользователя.

### Файлы Windows из Linux

Установщик может сжать систему (Compact OS / WOF): у такого файла атрибут
`FILE_ATTRIBUTE_REPARSE_POINT`, а содержимое лежит в сжатом потоке. `ntfs3` такие файлы только
читает: запись поверх (`cp`) уходит в обычный поток, а Windows и сам `ntfs3` продолжают читать
старое содержимое из сжатого — замена «не доживает». Заменять только удалением и созданием
заново; проверять — после перемонтирования, а не по кэшу. Атрибуты видны через
`getfattr -n system.ntfs_attrib`. Надёжнее вообще не писать в раздел Windows: обновления
кладутся на `LOLSSD` (FAT), а Windows забирает их сама [сделать].

### Драйверы для «любого компьютера»

Windows Update выключен, значит, драйверы должны лежать на SSD заранее. Они добавляются в
хранилище драйверов (`DISM /Add-Driver`), и PnP подхватывает их сам при первой загрузке
на новом железе.

| Класс | Что положить |
|---|---|
| GPU | INF-пакеты AMD, NVIDIA, Intel (без панелей управления, только драйвер) |
| Wi-Fi / Bluetooth | Intel, Realtek, MediaTek, Qualcomm — самые частые в ноутбуках |
| Ethernet | Realtek, Intel, USB-адаптеры Realtek/ASIX |
| Чипсет | AMD, Intel (основное) |

Альтернатива инъекции через DISM, которая работает и без Windows под рукой: положить INF-пакеты в
папку на разделе Windows (например, `C:\Drivers`, из Linux через `ntfs3`) и дописать её в значение
реестра `HKLM\SOFTWARE\Microsoft\Windows\CurrentVersion\DevicePath` — PnP ищет там драйверы
для новых устройств сам. [проверить] обходит ли он подпапки и как ведёт себя с подписью.

Драйверы GPU занимают гигабайты, это самая объёмная часть проекта. Возможная
оптимизация — набор драйверов, который собирающий выбирает под свои машины.

### Игра

Клиент Riot и лолка установлены в образ заранее. [проверить] Переживает ли Vanguard
загрузку на другом железе без переустановки.

## 5. Утилита для Linux (`lolssd`)

Лежит на разделе `LOLSSD`. **Один статический бинарник на Go**, без зависимостей: на чужой
машине может не оказаться `efibootmgr`, `jq` и прочего, поэтому всё нужное (efivarfs,
разбор `lsblk`/`/proc`, запись профиля) он делает сам. Нужен только `sudo` для команд,
которые трогают NVRAM или читают сведения о дисках.

| Команда | Что делает | Что меняет на хосте |
|---|---|---|
| `check` | требования из §3 | ничего |
| `boot` | находит ESP на том же диске, что и раздел `LOLSSD` (по GPT). Использует свою запись `Boot####` с меткой `lolssd` или создаёт её: `HD(ESP)/File(\EFI\BOOT\BOOTX64.EFI)`. Записи прошивки не берёт: у USB-записей часто нет GUID раздела, и не проверить, что они ведут на этот SSD. Ставит `BootNext` и перезагружает (`--no-reboot` — без перезагрузки). Отказывается работать, если запущен не с раздела `LOLSSD`. | одноразовый `BootNext`; одна запись `Boot####` с меткой `lolssd` (переиспользуется, в `BootOrder` не добавляется), её удаляет `boot --cleanup` |
| `profile` | описывает систему для режима Linux внутри Windows (§6), пишет профиль и образ загрузки ВМ на `LOLSSD` | ничего: образ собирает её же `mkinitcpio` с временным конфигом |

**Бинарник не трогает файлы хоста. Никогда.** Если какой-то функции нужно изменить хост,
это отдельная явная команда с описанием в документации, а не побочный эффект.

## 6. Linux внутри Windows (по желанию)

Windows загружена с USB, внутренние диски хоста для неё не системные и остаются Offline. Их
целиком получает **виртуальная машина**, и в ней грузится **настоящая система хоста**: её ядро,
initramfs, systemd, сервисы, `/home` — как на железе. Отличие одно: нет видеокарты, рисует
процессор (llvmpipe).

Почему ВМ, а не WSL. Первый вариант был на WSL (контейнер с системой хоста поверх ядра WSL,
Hyprland без экрана на d3d12): ядро чужое, модули DKMS приходилось собирать под него, графика
через d3d12 ломала часть программ, а контейнер отличался от загрузки с диска во множестве
мелочей. ВМ медленнее в графике, зато всё, что работает на железе, работает и в ней.

### Профиль хоста

`lolssd profile` (без sudo, ничего не меняет) пишет в `LOLSSD/profiles/<machine-id>.json`:
- точки монтирования с цепочкой устройств (раздел → LUKS → LVM) и PARTUUID — по ним Windows
  находит диски хоста;
- модель и серийный номер дисков — ВМ показывает их своими NVMe, ссылки `/dev/disk/by-id`
  совпадают;
- конфиги keyd (§7);
- PCI-адрес встроенной звуковой карты (`audio_pci`) — звуковая карта ВМ ставится на тот же адрес,
  и имена устройств PipeWire (`alsa_output.pci-0000_03_00.6…`) с настройками, завязанными на них,
  совпадают;
- **образ загрузки для ВМ** — UKI `LOLSSD/vm/<machine-id>.efi`, собранный её же `mkinitcpio` и
  ядром: конфиг системы плюс `nvme`, корень по `root=UUID=…` (имена дисков в ВМ другие), остальная
  командная строка — как сейчас, плюс консоль на `ttyS0` (журнал загрузки в Windows).

После обновления ядра на хосте профиль снимают заново: ядро в образе должно совпадать с модулями.

### Запуск: `lolssd-win desktop`

Ярлык «Linux desktop (host)». Сырой диск открывает только администратор, поэтому программа
перезапускает себя с запросом UAC, затем:
1. проверяет платформу гипервизора Windows (WHPX); нет — включает (DISM) и предлагает
   перезагрузку;
2. находит профиль этого компьютера (все его разделы есть на дисках) и номера дисков
   `\\.\PhysicalDriveN`;
3. готовит сеть (ниже), достаёт из UKI ядро, initramfs и командную строку;
4. запускает QEMU (`winctl.QEMUArgs`): `q35,vmport=off`, `-accel whpx`, `-cpu max` без
   VMX/SVM (с `-cpu host` WHPX падает с «Unexpected VP exit code 4»), половина памяти Windows,
   все процессоры кроме двух, прямой запуск ядра (`-kernel`), диски хоста как NVMe. Если QEMU
   падает в первые 15 секунд — второй запуск с `kernel-irqchip=off`;
5. на каждый монитор Windows (без повторов режима «Дублировать») — выход `virtio-gpu`, его
   VNC-сервер QEMU на `127.0.0.1:590N` и полноэкранный TigerVNC на этом мониторе.

Закрыть просмотрщик (Ctrl+Alt+M → Exit viewer) — отдать монитор Windows, Ctrl+Alt+F12 на нём —
вернуть Linux. Выключение Linux в ВМ закрывает и просмотрщики. Перезагружать Windows при
работающей ВМ нельзя: система хоста выключится некорректно.

Журналы в `C:\ProgramData\lolssd`: `lolssd-win.log`, `qemu.log` (командная строка и ошибки
QEMU), `serial.log` (загрузка Linux), `vncviewer-N.log` (нажатия клавиш, захват клавиатуры).

### Мониторы

Включён только первый выход virtio-gpu; остальные `lolssd-win` включает сам, запросом размера
по VNC (`SetDesktopSize`, `winctl.SetDesktopSize`) перед открытием просмотрщика. QEMU передаёт
размер системе как предпочтительный режим и помнит его. TigerVNC с `RemoteResize` такой запрос
не отправлял, а список `outputs` с размерами в QEMU 11 отдаёт указатель всех выходов планшету
последнего.

Для выходов `Virtual-N` в конфиге Hyprland обычно нет правил, и действует встроенное запасное
правило: предпочтительный режим, «auto-right», масштаб по плотности пикселей EDID. QEMU пишет
в EDID 100 точек на дюйм, поэтому масштаб 1, а выходы встают в ряд слева направо — в порядке
мониторов Windows.

### Ввод и всё, что ВМ передаёт системе при загрузке

У каждого выхода свой USB-планшет QEMU (`display`/`head`). Hyprland растягивает абсолютные
координаты устройства на всю раскладку, поэтому планшету нужна калибровочная матрица libinput.
Её, как и всё остальное, что нужно системе только в ВМ, QEMU передаёт **учётными данными
systemd через SMBIOS** — на диск хоста ничего не пишется:

| Учётные данные | Что делают |
|---|---|
| `udev.rules.70-lolssd-vm` | матрица `LIBINPUT_CALIBRATION_MATRIX` для планшета каждого выхода (раскладка «в ряд, масштаб 1»); скан-коду 0x76 PS/2-клавиатуры — `KEY_F23` (§7) |
| `tmpfiles.extra` | сведённый конфиг keyd в `/run/lolssd-vm/keyd/vm.conf` (§7) |
| `systemd.unit-dropin.keyd.service` | `BindReadOnlyPaths=/run/lolssd-vm/keyd:/etc/keyd` — keyd в ВМ читает его |

### Звук и сеть

- **Звук:** HDA с кодеком на вход и выход через DirectSound Windows, на PCI-адресе хоста (за
  нужным числом корневых портов PCIe, с пустой функцией 0, если адрес не нулевой).
- **Сеть:** адаптер TAP-Windows `lolssd` и общий доступ к интернету (ICS) с подключения, через
  которое идёт маршрут по умолчанию; ICS же раздаёт адрес по DHCP. Встроенная сеть QEMU (slirp)
  не годится: она принимает TCP гостя у себя и открывает новое соединение из Windows, и пакеты,
  которые собирает zapret (фальшивки с малым TTL, нарезка), до сети не доходят — TLS ломается.
  Драйвер ставится при первом запуске (`devcon`), при любой ошибке — запасная встроенная сеть
  и запись в журнале.

### Чего нет

- **Видеокарты.** Рисует llvmpipe, видео декодирует процессор: YouTube в высоком разрешении
  тянет плохо, звук при этом подлагивает.
- **Кадров больше ~30.** VNC-сервер QEMU рассылает изменения по таймеру не чаще раза в 30 мс,
  а после простоя разгоняется с интервала до 3 с. Опцией не меняется, только своя сборка QEMU.
- **Программ на hyprtoolkit** (hyprpaper при смене обоев): без 3D им не выделяется буфер.

## 7. Ввод: клавиатура, мышь, тачпад

Пока загружена Windows, устройствами ввода владеет она. Тачпад, скорость мыши, жесты — её
настройки. Клавиатура доходит до Linux так: полноэкранный TigerVNC забирает всю клавиатуру
(включая Win) и шлёт скан-коды (QEMU Extended Key Event) → VNC-сервер QEMU → PS/2-клавиатура
ВМ (`0001:0001`, «AT Translated Set 2 keyboard») → **keyd хоста** → Hyprland. Переназначения
делает keyd в ВМ, как на железе, с двумя поправками:

- **Сводный конфиг.** Windows и VNC сливают все клавиатуры в одну, а её идентификатор совпадает
  со встроенной клавиатурой ноутбука. keyd в ВМ получает один конфиг из всех файлов
  (`keymap.VMConfig`): секции объединяются, одна и та же клавиша — по общему конфигу (`*`).
  Например, у автора Menu → правая Super из `default.conf` и аккорд Copilot из `laptop.conf`.
  Отдельная правая Win не помогла бы: keyd выдаёт нажатые модификаторы левыми, правая Super
  получается только из правила `= rightmeta`.
- **F23.** PS/2-клавиатура QEMU не умеет F16–F23, а клавиша Copilot шлёт Win+Shift+F23. Windows
  переназначает F23 в F24 (`Scancode Map`, единственная запись, её пишет `lolssd-win logon` и
  просит перезагрузку), а правило udev в ВМ возвращает этому скан-коду F23.

Не переносится: настройки тачпада и мыши Linux, жесты (их назначают в настройках Windows),
пресеты input-remapper (переназначения кнопок мыши лучше записать в её память). Программы-
перехватчики ввода в Windows (AutoHotkey, Interception) проект не использует: рядом с Vanguard
это риск для аккаунта.

## 8. Сборка SSD

Цель: собрать SSD на той же машине с Linux, без Windows под рукой. Для сборки нужен QEMU,
для игры — ничего.

1. Скрипт урезает официальный ISO (через `wimlib`: смонтировать WIM, удалить пакеты,
   добавить драйверы, применить настройки реестра из §2–§4).
2. `autounattend.xml`: разметка (включая `LOLSSD`), локальный пользователь, пропуск OOBE,
   портативный режим, SAN policy, настройки из §2.
3. QEMU (UEFI через OVMF, виртуальный TPM через `swtpm`) ставит Windows **прямо на SSD**,
   подключённый к VM как сырой диск.
4. После установки — клиент Riot; QEMU, TigerVNC и драйвер TAP уже лежат в образе.
5. На `LOLSSD` копируется `lolssd` и документация.

**Игра ставится при сборке, целиком.** Официального офлайн-установщика у Riot нет, но
установщик принимает `--skip-to-install` (ставит Riot Client и игру без вопросов; им
пользуется, например, пакет Chocolatey — сторонние источники, у Riot подтверждения нет).
В QEMU запускается официальный установщик с этим ключом и докачивает всё; на реальном железе
остаются только обновления. [проверить] даст ли Riot Client докачать игру в виртуальной машине
(запуск игры там не нужен) и переживает ли Vanguard перенос на реальное железо.

## 9. Структура репозитория

```
cmd/lolssd/        утилита для Linux: check, boot, profile (с образом загрузки ВМ)
cmd/lolssd-win/    Windows-часть: nvram-guard, logon, restart, desktop (ВМ), сеть ВМ
winctl/            командная строка QEMU, правила udev для ВМ, запрос размера по VNC —
                   без вызовов Windows, проверяется тестами на Linux
keymap/            конфиг keyd для ВМ, Scancode Map
hostprofile/       профиль хоста — общий формат для обеих сторон
efi/               переменные и записи загрузки UEFI
build/             ISO (iso.sh, debloat.sh), установка на SSD (install.sh), QEMU и TAP для
                   образа (qemu.sh, tap.sh), настройка Windows при установке (setup/)
```
