# Лига на внешнем SSD: архитектура (черновик)

Внешний SSD с урезанной Windows и League of Legends. Подключаешь к любому компьютеру с Linux,
загружаешься с него и играешь. По желанию твой Linux продолжает работать внутри этой Windows:
та же установка с внутреннего диска, а не копия.

**Ничего не устанавливается в Linux заранее.** Всё, что нужно от системы, делает утилита,
лежащая на самом SSD: подключил, запустил с диска, готово. Утилита по возможности ничего не
меняет на хосте, а каждое изменение явно оговорено (§5).

> Проверено только на конкретном железе автора. На другом может не заработать, ничего не обещаю.

Пометка **[проверить]** означает предположение, которое ещё не проверено на железе.

---

## 1. Как этим пользоваться

**Только игра:**
1. Подключить SSD. Раздел `LOLSSD` монтируется автоматически, как обычная флешка.
2. `LOLSSD/host/lolssd check`: подходит ли машина (§3).
3. `LOLSSD/host/lolssd boot`: перезагрузиться в Windows на SSD. Без утилиты можно через
   меню загрузки прошивки (F12 / F8 / Esc).
4. Играть. Выключить, вытащить SSD, и следующая загрузка, как обычно, идёт в Linux.

**С Linux внутри Windows (по желанию):**
1. Один раз на этой машине: `lolssd profile` описывает твою систему и сохраняет описание на SSD (§6).
2. `lolssd boot`, и в Windows твой Linux поднимается автоматически.

## 2. Обязательства перед хостом

Суть проекта: SSD можно подключить к чужой машине, и он ей ничего не сломает.

| Риск | Как SSD его закрывает |
|---|---|
| Windows монтирует внутренние диски хоста и пишет на них (включая ESP хоста) | Портативный режим Windows (`PortableOperatingSystem`) плюс SAN policy «Offline Internal»: внутренние диски остаются Offline. Исключение — режим «Linux внутри Windows», где `wsl --mount` отдаёт разделы Linux в WSL, но только их и только по профилю (§6). |
| Windows добавляет себя в NVRAM хоста и встаёт первой в `BootOrder` | Загрузчик лежит по запасному пути `\EFI\BOOT\BOOTX64.EFI` на ESP самого SSD, запись в NVRAM не нужна. При каждом старте Windows `lolssd-win nvram-guard` убирает из `BootOrder` все записи, ведущие на ESP SSD (по GUID раздела), а созданные Windows удаляет. Запись `lolssd` от утилиты хоста только убирается из порядка. [проверить] Создаёт ли Windows такую запись при загрузке с USB. |
| Часы хоста уезжают на смещение часового пояса | `RealTimeIsUniversal=1`: Windows считает RTC временем UTC, как Linux. |
| После Windows NTFS «грязный», висит гибернация | Fast Startup и гибернация выключены. Портативный режим делает это и сам. |
| BitLocker / шифрование устройства привязывается к TPM хоста | Шифрование выключено и заблокировано политикой. |
| Windows внезапно обновляется и перезагружается | Обновления выключены полностью. Windows заморожена. |
| Linux хоста был в гибернации, и WSL монтирует его корень на запись | Портит файловую систему. Запуск Linux внутри Windows проверяет, что ФС чистая, и отказывается иначе (§6). |

## 3. Требования к компьютеру

Это требования к прошивке, не к Linux. `lolssd check` проверяет всё, что видно из Linux.

| Что | Почему | Как проверяет `check` |
|---|---|---|
| UEFI (не Legacy/CSM) | Vanguard требует UEFI (VAN 9005) | `/sys/firmware/efi` |
| TPM 2.0 (AMD fTPM / Intel PTT) | Vanguard (VAN 9001) | `/sys/class/tpm/tpm0/tpm_version_major` |
| Виртуализация (SVM / VT-x) | VBS / HVCI (VAN 9005), WSL | флаги `svm`/`vmx` в `/proc/cpuinfo` плюс `dmesg` на «disabled by BIOS» |
| **Secure Boot** [проверить] | возможно, требуется Vanguard'у | переменная `SecureBoot` в efivarfs. Если нужен, а Linux хоста не подписан, Secure Boot придётся включать перед игрой и выключать после. Это ручное действие в BIOS. |
| Порт USB 10 Гбит/с | скорость | скорость SSD в `/sys/bus/usb/devices/*/speed` |
| Память | для режима Linux внутри Windows | `/proc/meminfo` |

[проверить] Требования различаются для Windows 10 и 11. В справке Riot про TPM (VAN 9001)
стоит «Win 11 Only», то есть на Windows 10 требований может быть меньше, и это расширит
круг подходящих машин. Нужно проверить, обязателен ли на Windows 10 Secure Boot.

## 4. Содержимое SSD

### Разметка

| Раздел | Размер | Назначение |
|---|---|---|
| ESP, FAT32 | 260–512 МБ | `\EFI\BOOT\BOOTX64.EFI` + `\EFI\Microsoft\Boot` |
| `LOLSSD`, FAT32 | 256 МБ | утилита для Linux, профили хостов, документация. FAT32 читается везде: и в Linux, и в Windows. |
| MSR | 16 МБ | служебный раздел Windows |
| Windows, NTFS | остальное | система, игра, пусковой WSL-дистрибутив |

Диск: NVMe в USB-корпусе (UASP + TRIM) или SATA в корпусе. Минимум ~64 ГБ без Linux
внутри Windows, нормально 128 ГБ.

### Windows

- **Версия:** 10 или 11 по результату проверки требований Vanguard (§3). Но для режима
  Linux внутри Windows удобнее 11: [проверить] на 10 нет `networkingMode=mirrored` и,
  возможно, `autoMemoryReclaim`.
- **Сборка:** урезается самостоятельно из официального ISO (по образцу tiny11builder). Убрать:
  приложения из магазина, рекламу, телеметрию, OneDrive. **Оставить:** VBS / HVCI, поддержку
  TPM, Virtual Machine Platform (WSL), Defender (если его отсутствие мешает HVCI [проверить]).
- **Обновления:** выключены службы `wuauserv`, `UsoSvc`, `WaaSMedicSvc` и политиками.
- **Без учётной записи Microsoft:** локальный пользователь, автоматический вход.
- **Активация:** если в прошивке хоста зашит ключ OEM (таблица ACPI MSDM) и редакция совпадает,
  Windows активируется сама. Иначе работает без активации, с водяным знаком.
  Лицензирование — ответственность пользователя.

### Файлы Windows из Linux

Установщик может сжать систему (Compact OS / WOF): у такого файла атрибут
`FILE_ATTRIBUTE_REPARSE_POINT`, а содержимое лежит в сжатом потоке. `ntfs3` такие файлы только
читает: запись поверх (`cp`) уходит в обычный поток, а Windows и сам `ntfs3` продолжают читать
старое содержимое из сжатого — замена «не доживает». Заменять только удалением и созданием
заново; проверять — после перемонтирования, а не по кэшу. Атрибуты видны через
`getfattr -n system.ntfs_attrib`. Надёжнее вообще не писать в раздел Windows: обновления
кладутся на `LOLSSD` (FAT), а Windows забирает их сама [сделать].

### Драйверы для «любого компьютера»

Windows Update выключен, значит, драйверы должны лежать на SSD заранее. Они добавляются в
хранилище драйверов (`DISM /Add-Driver`), и PnP подхватывает их сам при первой загрузке
на новом железе.

| Класс | Что положить |
|---|---|
| GPU | INF-пакеты AMD, NVIDIA, Intel (без панелей управления, только драйвер) |
| Wi-Fi / Bluetooth | Intel, Realtek, MediaTek, Qualcomm — самые частые в ноутбуках |
| Ethernet | Realtek, Intel, USB-адаптеры Realtek/ASIX |
| Чипсет | AMD, Intel (основное) |

Альтернатива инъекции через DISM, которая работает и без Windows под рукой: положить INF-пакеты в
папку на разделе Windows (например, `C:\Drivers`, из Linux через `ntfs3`) и дописать её в значение
реестра `HKLM\SOFTWARE\Microsoft\Windows\CurrentVersion\DevicePath` — PnP ищет там драйверы
для новых устройств сам. [проверить] обходит ли он подпапки и как ведёт себя с подписью.

Драйверы GPU занимают гигабайты, это самая объёмная часть проекта. Возможная
оптимизация — набор драйверов, который собирающий выбирает под свои машины.

## 5. Утилита для Linux (`lolssd`)

Лежит на разделе `LOLSSD`. **Один статический бинарник на Go**, без зависимостей: на чужой
машине может не оказаться `efibootmgr`, `jq` и прочего, поэтому всё нужное (efivarfs,
разбор `lsblk`/`/proc`, запись профиля) он делает сам. Нужен только `sudo` для команд,
которые трогают NVRAM или читают сведения о дисках.

| Команда | Что делает | Что меняет на хосте |
|---|---|---|
| `check` | требования из §3 + чистота ФС корня (§6) | ничего |
| `boot` | находит ESP на том же диске, что и раздел `LOLSSD` (по GPT). Использует свою запись `Boot####` с меткой `lolssd` или создаёт её: `HD(ESP)/File(\EFI\BOOT\BOOTX64.EFI)`. Записи прошивки не берёт: у USB-записей часто нет GUID раздела, и не проверить, что они ведут на этот SSD. Ставит `BootNext` и перезагружает (`--no-reboot` — без перезагрузки). Отказывается работать, если запущен не с раздела `LOLSSD`. | одноразовый `BootNext`; одна запись `Boot####` с меткой `lolssd` (переиспользуется, в `BootOrder` не добавляется), её удаляет `boot --cleanup` |
| `profile` | описывает систему для режима Linux внутри Windows (§6) и пишет профиль на `LOLSSD` | ничего, только читает |

**Бинарник не трогает файлы хоста. Никогда.** Если какой-то функции нужно изменить хост,
это отдельная явная команда с описанием в документации, а не побочный эффект.

## 6. Linux внутри Windows (по желанию)

Windows загружена с USB, поэтому внутренние диски хоста для неё не системные, и
`wsl --mount` может отдать разделы Linux в WSL. Там пусковой дистрибутив запускает
**настоящую систему хоста** через `systemd-nspawn`: те же пакеты, конфиги, `/home`.

### Профиль хоста

`lolssd profile` собирает и пишет в `LOLSSD/profiles/<machine-id>.json`:

| Что | Откуда | Зачем |
|---|---|---|
| Диск: серийный номер и модель | `/sys/block/*/device` | найти тот же диск в Windows (`PHYSICALDRIVE<N>` меняется) |
| Точки монтирования: раздел, ФС, опции | `/proc/self/mountinfo`, `findmnt` | `/`, `/home` и прочее, кроме `/boot` и ESP |
| btrfs: подтомы | опции `subvol=` | `-o subvol=@` при монтировании |
| LUKS: UUID контейнеров | `/sys/block/dm-*`, `cryptsetup` | монтировать с `--bare` и открывать внутри WSL (спросит пароль) |
| LVM | `/sys/block/dm-*` | `vgchange -ay` внутри WSL |
| Пользователь: имя, UID, GID | тот, кто запустил `sudo` (`SUDO_UID`) | запуск сеанса от того же UID |
| Сеанс: композитор | `XDG_CURRENT_DESKTOP`, процессы | выбор режима ниже |
| Mesa с d3d12 | наличие драйвера `d3d12` в системной Mesa | ускорение графики, иначе llvmpipe и предупреждение |
| Объём RAM | `/proc/meminfo` | лимит памяти WSL |
| swap (разделы и файлы, кроме zram) | `/proc/swaps` | проверка гибернации перед монтированием |

`profile` запускается **без sudo**: всё нужное читается обычным пользователем, а профиль
описывает именно его сеанс. Мониторы через USB-доки (MST) получают порты вроде `DP-8`,
которые меняются от подключения к подключению, поэтому сопоставление идёт по EDID.

Профиль — это данные, а не команды: пусковой дистрибутив сам решает, что выполнить.

### Запуск в Windows

1. `lolssd-win mount` — задание планировщика при входе администратора (автовход), с повышенными
   правами, как требует `wsl --mount`:
   - находит том `LOLSSD` по метке и профили в `profiles\`;
   - читает GPT всех дисков, кроме системного (сырое чтение работает и для дисков в Offline);
   - выбирает профиль, **все PARTUUID** которого нашлись на этом компьютере (из нескольких —
     самый свежий). Серийный номер не годится: для NVMe Windows иногда отдаёт EUI-64 вместо него;
   - подключает нужные диски целиком: `wsl --mount \\.\PHYSICALDRIVE<N> --bare`. Разделы, LUKS,
     LVM и подтомы поднимает уже пусковой дистрибутив, находя разделы по PARTUUID;
   - кладёт выбранный профиль в `C:\ProgramData\lolssd\active-profile.json`
     (в WSL — `/mnt/c/ProgramData/lolssd/`).
   Профиля для этого компьютера нет — режим не включался, выход без ошибки.
2. Пусковой дистрибутив — Debian stable на SSD (от хоста не зависит; стабильный выпуск, чтобы
   не протухал, пока диск лежит в ящике), с пакетами `systemd-container`, `cryptsetup`, `lvm2`,
   `libxkbcommon-tools` и инструментом `lolssd-wsl` (запускается от root):
   - **`up`** — поднимает систему хоста в `/run/lolssd/root`:
     1. разделы находятся по PARTUUID через GPT всех дисков, которые видит WSL (без udev/blkid);
     2. цепочки устройств поднимаются снизу вверх: LUKS (`cryptsetup open`, спросит пароль),
        LVM (`vgchange -ay`);
     3. **проверки до любой записи:** в swap-разделах нет образа гибернации (`S1SUSPEND` и т. п.
        вместо `SWAPSPACE2`); у ext3/ext4 нет `needs_recovery` и ошибок в суперблоке; swap-файлы
        проверяются через монтирование только для чтения **без восстановления журналов**
        (`noload` / `rescue=nologreplay` / `norecovery`), чтобы на диск не ушло ни байта;
     4. если хоста выключили не чисто — отказ с объяснением, всё опускается обратно;
     5. иначе ФС монтируются на запись, родители раньше детей, с подтомами btrfs.
   - **`down`** — отмонтировать, деактивировать LVM, закрыть LUKS.
   - **`run -- команда`** — `up`, затем `systemd-nspawn` **без** `--boot` от пользователя профиля:
     системные службы хоста не запускаются. Всё WSL-шное пробрасывается под `/run/lolssd-wsl`
     (tmpfs контейнера), чтобы точки монтирования не создавались на диске хоста: `/mnt/wslg`
     (Wayland, X11, PulseAudio), `/usr/lib/wsl` (библиотеки d3d12), `/dev/dxg` (GPU-PV, если есть).
     Окружение: `WAYLAND_DISPLAY`, `DISPLAY`, `XDG_RUNTIME_DIR`, `PULSE_SERVER`,
     `GALLIUM_DRIVER=d3d12`, `LD_LIBRARY_PATH`, `LOLSSD=wsl` (по ней конфиги хоста узнают режим).
     `--link-journal=no --timezone=off --resolv-conf=bind-host`: nspawn ничего не копирует в `/etc`
     и `/var` хоста.

### Два уровня

| Режим | Что | Где работает |
|---|---|---|
| **Приложения** | отдельные программы хоста окнами WSLg на рабочем столе Windows: браузер, терминал, Discord | любой дистрибутив, любой рабочий стол |
| **Рабочий стол** | композитор хоста без экрана (headless), каждый выход — полноэкранный VNC-просмотрщик на своём мониторе | Hyprland (сделано); wlroots, GNOME, KDE — см. ниже |

Режим «Рабочий стол»:
- Композитор запускается с **конфигом-обёрткой с SSD**, который подключает конфиг пользователя
  и переопределяет то, что связано с железом (мониторы, яркость, батарея). Обёртка
  пробрасывается в контейнер, конфиги хоста не меняются.
- Клавиша Super: в Windows выключены системные Win-сочетания (`NoWinKeys`).

#### Как композитор работает без экрана

Вложить композитор в WSLg нельзя: WSLg принимает только буферы в общей памяти, без
`zwp_linux_dmabuf_v1`, и aquamarine падает с «no allocator available». Устройства вывода (DRM/KMS)
в WSL тоже нет. Работает так (идея — проект hyprland-wsl, код свой, у того нет лицензии):

```
Windows: TigerVNC на весь экран, по одному на монитор   lolssd-win desktop
   └─ 127.0.0.1:5901, 5902, …  (WSL пробрасывает localhost в Windows)
wayvnc, по одному на выход HEADLESS-N                     пусковой Debian
Hyprland хоста на headless-бэкенде                        nspawn, система хоста
   └─ пропатченный aquamarine: буферы на vgem
vgem — виртуальное DRM-устройство ядра WSL; рисует Mesa d3d12 через /dev/dxg (или llvmpipe)
```

- **vgem** даёт DRM-устройство без экрана: на нём выделяются буферы и открывается EGL. С d3d12
  буферы на деле принадлежат Direct3D 12, vgem лишь «одалживает» имя.
- **Патч aquamarine** (`build/hypr/aquamarine-headless-device.patch`): headless-бэкенд открывает
  `AQ_HEADLESS_DRM_DEVICE`, аллокатор остаётся на основном узле (render-узел vgem выделять не
  даёт), GBM при отказе всех вариантов просит простейший буфер (иначе d3d12 не даёт ничего),
  размеры выходов — `AQ_HEADLESS_MODES=WxH,WxH,…` по мониторам Windows. Членов классов патч не
  добавляет, библиотека совместима по ABI со штатной.
- **Сборка патча** — при первом запуске на каждую версию aquamarine хоста, внутри системы хоста
  её компилятором и заголовками (на Arch всё нужное приходит вместе с Hyprland), результат — в
  кэше пускового дистрибутива `/var/cache/lolssd/aquamarine/<версия>`. На диск хоста не пишется
  ничего; Hyprland получает библиотеку через `LD_LIBRARY_PATH`. [проверить] дистрибутивы, где у
  Hyprland есть file capability (Debian): там загрузчик `LD_LIBRARY_PATH` игнорирует, нужна
  подмена через приватное пространство монтирования.
- **XDG_RUNTIME_DIR** сеанса короткий (`/run/lolssd/xdg` → `/run/user/<uid>` в контейнере):
  через каталог WSLg путь к сокету Hyprland превышал 108 байт. Этот же каталог видит wayvnc.
- **wayvnc** из пускового Debian, по одному на выход, только на 127.0.0.1 без пароля; упавший
  перезапускается.
- **TigerVNC** для Windows на весь экран забирает всю клавиатуру, включая Win: она становится
  Super в Hyprland.

**GPU в контейнере** [проверить]: d3d12 через `libdxcore` ищет драйвер видеокарты по жёсткому пути
`/usr/lib/wsl/drivers` (так же в Docker под WSL: `/usr/lib/wsl` монтируют по тому же пути). В
системе хоста этого каталога нет, а создать точку монтирования — значит записать на диск хоста.
Пока Hyprland при неудаче с d3d12 перезапускается на llvmpipe (CPU).

Цена: каждый кадр читается из GPU, кодируется и декодируется (это главная потеря на GPU);
размер экрана фиксируется при запуске сеанса.

Другие композиторы — та же схема, отличается только запуск (пока не сделано):

| Композитор | Как без экрана | Захват |
|---|---|---|
| Hyprland | патч aquamarine (выше) | wayvnc |
| Sway, river, labwc и др. на wlroots | штатно: `WLR_BACKENDS=headless`, `WLR_RENDER_DRM_DEVICE=/dev/dri/cardN` | wayvnc |
| GNOME | mutter `--headless` с виртуальными мониторами | gnome-remote-desktop (RDP) → `mstsc` [проверить] |
| KDE | `kwin_wayland --virtual` | krfb или KRdp [проверить] |

#### Linux поверх Windows, отдельно на каждом мониторе

На каждом мониторе Windows — свой полноэкранный TigerVNC со своим выходом Hyprland. Внутри
всё делает композитор хоста. Виртуальные рабочие столы Windows не используются: они
переключаются сразу на всех мониторах. Вместо них каждый монитор независимо «отдаётся» Linux
или Windows:

| Действие | Что происходит |
|---|---|
| Отдать монитор Windows | закрыть его просмотрщик: F8 → Exit viewer в TigerVNC или Ctrl+Alt+F12 |
| Вернуть монитор Linux | Ctrl+Alt+F12 на этом мониторе — просмотрщик открывается снова |

Выход в Hyprland при этом **не удаляется**. Удалённый и созданный заново выход получил бы
новое имя (`HEADLESS-4` вместо `HEADLESS-2`), и переведённые правила конфига перестали бы к нему
относиться. Цена: рабочие области на отданном мониторе остаются, и на него можно увести
фокус сочетанием клавиш — тогда ничего не видно, пока монитор не вернуть.

#### Перевод правил, привязанных к мониторам

Без экрана выходы называются `HEADLESS-1`, `HEADLESS-2` и т. д., а не `eDP-1` или
`HDMI-A-1`, и у них другой `desc:`. Переименовать их нельзя: `hyprctl output create` принимает
только бэкенд. Значит, правила конфига переводятся на новые имена.

Пример из конфига автора:
```lua
hl.monitor({ output = "eDP-1", ... })                                  -- активен → HEADLESS-1
hl.monitor({ output = "HDMI-A-1", ... })                               -- не подключён → не трогать
hl.monitor({ output = "desc:LG Electronics LG HDR WFHD 0x00043804", ... }) -- подключён → HEADLESS-2
```

1. **Профиль (Linux, только чтение)** сохраняет активные мониторы: порт, `desc`, сырой EDID
   из `/sys/class/drm/card*-<порт>/edid`, позицию, масштаб, частоту.
2. **Windows** (`lolssd-win mount`) пишет `C:\ProgramData\lolssd\monitors.json`: активные мониторы
   из CCD API (`QueryDisplayConfig`), позиция, размер, частота и EDID из реестра
   (`Enum\DISPLAY\...\Device Parameters\EDID`) по пути устройства монитора. Порядок — слева
   направо; номер в списке задаёт номер выхода (`HEADLESS-1` — первый).
   Сопоставление по сырому EDID точное. Описания вроде «Samsung Display Corp.» не нужно
   сверять со строками PNP ID, а у встроенной панели серийного номера может не быть вовсе.
3. **Таблица соответствий** `порт / desc → HEADLESS-N` строится только для мониторов, которые
   есть и в профиле, и в Windows сейчас. Правила для остальных не трогаются: композитор и так
   игнорирует правила для отсутствующих мониторов.
4. **Применение без изменения файлов хоста:**
   - Lua-конфиг: обёртка загружается перед конфигом пользователя и подменяет глобальную `hl`
     прокси (рекурсивно, с сохранением вызываемых таблиц). В аргументах любого вызова, на любой
     глубине таблиц, заменяются точные имена портов и `desc:` по префиксу. Так перевод не зависит
     от того, какие функции API принимают имя монитора. Дополнительные выходы создаются из
     `hl.on("hyprland.start")`. Проверено на Lua 5.4 с поддельным API и на конфиге автора;
   - hyprlang (`.conf`): копия дерева конфигов (по `source`, с глобами и `~`) в `/run/lolssd/session`
     с заменой имён; Hyprland запускается с `--config` на копию, оригинал не трогается.
     Дополнительные выходы — строками `exec-once = hyprctl output create headless`.

Правила работают только для мониторов, которые были подключены при `lolssd profile`: EDID
остальных хост не знает. Чтобы покрыть все, профиль снимают с подключёнными мониторами.
5. Позиции выходов берутся из раскладки мониторов в Windows, масштаб — из профиля.

Не покрыто, на будущее: имена мониторов в панелях (waybar `"output"`) и в скриптах
пользователя (`hyprctl dispatch focusmonitor DP-1`). Панели можно переводить так же, копией
конфига. Скрипты — нет, это остаётся на пользователе.

#### Запуск из Windows: `lolssd-win desktop`

Ярлык «Linux desktop (host)». Берёт текущие мониторы из CCD API (раскладку могли поменять после
входа) и передаёт их сеансу через `WSLENV` (`LOLSSD_MONITORS`), запускает
`lolssd-wsl session` в видимой консоли (ход первой сборки aquamarine, пароль LUKS, ошибки) и,
как только wayvnc монитора отвечает, открывает на нём TigerVNC (`-FullScreen
-FullScreenMode=Current`, окно сначала ставится на этот монитор). Ctrl+Alt+F12 закрывает
просмотрщик под курсором или открывает его снова. Выход из Hyprland закрывает всё.

Жест тачпада: в «Параметры → Bluetooth и устройства → Сенсорная панель → Расширенные жесты»
назначить свайп на сочетание Ctrl+Alt+F12. Пока вручную; [проверить] где Windows хранит эти
настройки, чтобы выставлять их из профиля.

[проверить]:
- доходит ли Ctrl+Alt+F12 до Windows, пока полноэкранный TigerVNC держит клавиатуру (если нет —
  F8 → Exit viewer);
- что TigerVNC попадает на нужный монитор при разном DPI мониторов;
- фокус и захват мыши между Linux и игрой без рамки на соседнем мониторе.

### Защита от поломки хоста изнутри контейнера

Обновление ядра изнутри контейнера сломает загрузку хоста: модули в `/usr/lib/modules`
обновятся, а ядро и initramfs на ESP — нет, потому что ESP не смонтирован. Поэтому в
контейнер подкладывается хук пакетного менеджера, который прерывает транзакцию, затрагивающую
ядро или `/boot`. Для Arch это overlay поверх `/etc/pacman.d` хоста с верхним слоем в tmpfs:
pacman хук видит, а на диск хоста он не попадает.

| Дистрибутив | Механизм |
|---|---|
| Arch | `PreTransaction`-хук с `AbortOnFail` в `/etc/pacman.d/hooks/` |
| Debian / Ubuntu | `DPkg::Pre-Install-Pkgs` в `/etc/apt/apt.conf.d/` [проверить] |
| Fedora | [проверить] |

Остальные дистрибутивы: предупреждение в документации «не обновляй систему из режима WSL».

### `.wslconfig`

Пишет `lolssd-win mount` до первого `wsl --mount` (он запускает ВМ WSL, а конфиг читается при
старте): `memory` = половина памяти Windows (не меньше 4 ГиБ), `swap=4GB`, `guiApplications`,
`autoMemoryReclaim=gradual` [проверить на выбранной Windows]. Файл помечен первой строкой;
`.wslconfig` без пометки (написанный пользователем) не трогается.

### Запуск сеанса

`lolssd-wsl session`: `up`, сопоставление мониторов, обёртка конфига, загрузка vgem, сборка или
кэш пропатченного aquamarine, затем через тот же nspawn `Hyprland --config <обёртка>` на
headless-бэкенде, и wayvnc на каждый выход (`cmd/lolssd-wsl/desktop.go`).

## 7. Ввод: клавиатура, мышь, тачпад

### Кто владеет устройствами

Пока загружена Windows, устройствами ввода владеет **только она**. Linux внутри WSL получает
от WSLg уже обработанные события через RDP:

| Что | Чьи настройки действуют |
|---|---|
| Раскладка клавиатуры, сочетания клавиш в окнах Linux | Linux (WSLg передаёт скан-коды) |
| Тачпад: тап, прокрутка, жесты, ускорение | Windows (Precision Touchpad обрабатывает всё до RDP) |
| Скорость и ускорение мыши | Windows |
| Переназначения кнопок (input-remapper, keyd) | не действуют: они работают с устройствами `evdev`, которых в WSL нет |
| Ввод в игре | только Windows |

Пробросить устройства в Linux нельзя: встроенные клавиатура и тачпад ноутбуков висят на I2C/PS2,
а не на USB (usbipd), и вложенный композитор всё равно берёт ввод у родительского. Стрим игры
в Linux (Sunshine → Moonlight) добавил бы задержку, синтетический ввод в игру рядом с Vanguard
и нагрузку на GPU, а настройки тачпада и мыши всё равно остались бы виндовыми.

Поэтому настройки ввода должны жить там, где их видят обе системы, — **в железе**, — или
**переноситься из Linux в Windows**.

### Слои, от лучшего к худшему

| Слой | Что | Где работает | Vanguard |
|---|---|---|---|
| Память устройства | профили мыши/клавиатуры со встроенной памятью (переназначения кнопок, DPI, переключение профилей кнопкой). Пишутся один раз утилитой производителя | везде, без софта | безопасно: это железо |
| Встроенные механизмы Windows | раскладки, `Scancode Map` (переназначение клавиш 1:1 на уровне драйвера `kbdclass`), настройки тачпада и указателя | Windows | безопасно: стандартные средства ОС |
| Программы-переназначатели в Windows | AutoHotkey, Interception и т. п. | Windows | **не используем**: Interception известен по читам, любой перехват ввода рядом с Vanguard — риск для аккаунта |

### Что делает проект

- **Драйверы.** На SSD — только классовые драйверы Windows (HID, I2C HID для тачпадов) и
  драйверы чипсетов из набора (§4). Фирменный софт периферии (Synapse, G Hub) в образ не входит.
- **Клавиши: переназначения keyd из профиля** (пакет `keymap`). `lolssd profile` сохраняет
  конфиги keyd как есть и раскладку композитора (RMLVO); разбирают их обе стороны:

  | Что | Где применяется | Как |
  |---|---|---|
  | Транспорт Meta: левая/правая Win → F13/F14 | Windows, `Scancode Map` | иначе Windows перехватывает Win и до Linux она не доходит. Побочно Win не выкидывает из игры в «Пуск» (он остаётся на Ctrl+Esc) |
  | F13/F14 → `Super_L`/`Super_R` (модификатор Super) | раскладка Hyprland | `xkbcli compile-keymap` с RMLVO пользователя + дописанные клавиши → `kb_file` в обёртке |
  | 1:1 из `[main]` (`compose = rightmeta`) | Windows, `Scancode Map` | действует и в игре, и в Linux; цели-Meta идут через транспорт (F14) |
  | сочетания, дающие модификатор (`f23+leftshift+leftmeta = rightmeta` — клавиша Copilot) | обёртка Lua-конфига Hyprland | пока зажата клавиша-немодификатор сочетания (F23): `hl.is_key_down` видит цель (`Super_R`) и не видит модификаторы сочетания; к привязкам «SUPER + K» добавляются варианты с лишними модификаторами сочетания («SHIFT + SUPER + K»). Своя привязка пользователя на тот же вариант разводится по F23, если обе — функции, иначе остаётся как есть |
  | слои, `overload`, макросы, цели без скан-кода в Windows (`menu`) | — | не переносятся, `lolssd profile` и журнал `lolssd-win` их перечисляют |

  `Scancode Map` один на все клавиатуры: правила keyd для отдельных клавиатур при конфликте
  уступают правилам для всех (`*`), это тоже попадает в заметки. Его читает драйвер при загрузке:
  `lolssd-win mount` записывает его при смене профиля и просит перезагрузить Windows.
  В пусковом дистрибутиве нужны `libxkbcommon` (`xkbcli`) и `xkeyboard-config`.
- **Перенос остальных настроек из профиля** [сделать]: `lolssd profile` читает, контроллер при
  входе применяет в Windows:

  | В Linux | В Windows |
  |---|---|
  | раскладки XKB (`input:kb_layout` композитора / `localectl`) и переключение — для игры | раскладки пользователя (`HKCU\Keyboard Layout\Preload`) |
  | тачпад: тап, естественная прокрутка, скорость (`input:touchpad:*`) | настройки Precision Touchpad [проверить, где хранятся] |
  | жест переключения рабочих областей (число пальцев) | расширенные жесты → Ctrl+Alt+F12 (§6) [проверить] |
  | скорость/ускорение мыши (`input:sensitivity`, `accel_profile`) | скорость указателя, «повышенная точность» вкл./выкл. |

  Что не переносится — пресеты input-remapper, — `lolssd profile`
  перечисляет с советом: переназначения кнопок мыши записать в её память, если она умеет.
- **Документация** [сделать]: «Профили мыши» — как перенести пресеты input-remapper в память
  мыши (пример: Razer Basilisk V3 хранит 5 профилей, пишутся Razer Synapse один раз, переключаются
  кнопкой снизу и работают и в Windows, и в Linux).

## 8. Сборка SSD

Цель: собрать SSD на той же машине с Linux, без Windows под рукой. Для сборки нужен QEMU,
для игры — ничего.

1. Скрипт урезает официальный ISO (через `wimlib`: смонтировать WIM, удалить пакеты,
   добавить драйверы, применить настройки реестра из §2–§4).
2. `autounattend.xml`: разметка (включая `LOLSSD`), локальный пользователь, пропуск OOBE,
   портативный режим, SAN policy, настройки из §2.
3. QEMU (UEFI через OVMF, виртуальный TPM через `swtpm`) ставит Windows **прямо на SSD**,
   подключённый к VM как сырой диск.
4. После установки: WSL и пусковой дистрибутив, клиент Riot, затем `sysprep /generalize`,
   чтобы при первой загрузке на реальном железе Windows заново определила оборудование.
5. На `LOLSSD` копируется `lolssd` и документация.

**Игра ставится при сборке, целиком.** Официального офлайн-установщика у Riot нет, но
установщик принимает `--skip-to-install` (ставит Riot Client и игру без вопросов; им
пользуется, например, пакет Chocolatey — сторонние источники, у Riot подтверждения нет).
В QEMU запускается официальный установщик с этим ключом и докачивает всё; на реальном железе
остаются только обновления. [проверить] даст ли Riot Client докачать игру в виртуальной машине
(запуск игры там не нужен) и переживает ли Vanguard перенос на реальное железо.

**WSL офлайн.** `wsl.exe` в Windows — заглушка, сам WSL ставится пакетом. В образ кладётся MSI
WSL с GitHub Microsoft, а пусковой дистрибутив импортируется (`wsl --import lolssd ...
dist/wsl/lolssd.tar`) при первом входе: после включения компонентов нужна перезагрузка.

## 11. Открытые вопросы

1. Windows 10 или 11 (прототип 2 против удобства WSL на 11).
2. Насколько «любой компьютер»: везти драйверы для всех GPU или выбирать при сборке.
3. Автоматизировать ли установку игры, или это ручной шаг.
4. Название проекта (утилита пока `lolssd`).
